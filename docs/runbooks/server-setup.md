# Runbook: server setup

How the production VPS was set up (M0-09, November 2026). Follow it top to bottom to rebuild the server from a fresh Ubuntu install. Hosting choice: ADR-0040.

This repo is public: the server's IP address, its host key fingerprint and every password stay in the password manager, never here. "The VPS" below means `deploy@<vps-ip>`.

**Golden rule:** whenever a step touches SSH or the firewall, keep the current session open, and prove a **new** login works before closing anything. If you're locked out anyway, the provider's browser console (root and the root password) still works.

## 0. Before you start

- A fresh **Ubuntu 24.04 LTS** (noble), x86_64, on a KVM VPS. The root password is in the password manager; it's only for the provider's console.
- On your laptop, your own SSH key **with a passphrase**: `ssh-keygen -t ed25519 -C "quode-vps"`. Don't use keys generated by the provider's panel.
- Save the server's host key fingerprint (shown on the first SSH connection) in the password manager, and compare it on every new machine.

## 1. Update the system (as root, console or first SSH)

```bash
apt update && apt full-upgrade -y
[ -f /var/run/reboot-required ] && reboot
```

## 2. Create the `deploy` user

```bash
adduser deploy              # long password, saved in the password manager: sudo asks for it
usermod -aG sudo deploy
```

## 3. Install your key for `deploy` (from the laptop)

PowerShell on Windows (asks for the `deploy` password once):

```powershell
type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh deploy@<vps-ip> "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
```

Check: `ssh deploy@<vps-ip>` asks only for the key's passphrase, and `sudo -v` asks for the `deploy` password.

From here on, work as `deploy` with `sudo`.

## 4. SSH: keys only, no root login

```bash
sudo tee /etc/ssh/sshd_config.d/00-quode-hardening.conf >/dev/null <<'EOF'
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
AuthenticationMethods publickey
EOF
sudo sshd -t && echo CONFIG OK
sudo sshd -T | grep -Ei '^(permitrootlogin|passwordauthentication|kbdinteractiveauthentication|pubkeyauthentication)'
sudo systemctl restart ssh
```

- **Why the `00-` prefix:** cloud images ship `50-cloud-init.conf` with `PasswordAuthentication yes`, and sshd keeps the **first** value it reads. The `00-` file is read first, so it wins.
- **Check, from a new laptop window, with the old session still open:** `ssh deploy@<vps-ip>` works, and `ssh root@<vps-ip>` fails with `Permission denied (publickey)`.
- **To undo, from the open session:** `sudo rm /etc/ssh/sshd_config.d/00-quode-hardening.conf && sudo systemctl restart ssh`.

## 5. Firewall: only 22, 80, 443

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status verbose     # active; 22, 80, 443 allowed for v4 and v6
```

Then test a new SSH login again.

**Docker publishes ports past ufw** (its own iptables rules). So `deploy/compose.yml` (M0-10) must publish only Caddy on public interfaces (80/443). Postgres publishes only `127.0.0.1:5432` and the backend only Actuator on `127.0.0.1:8081`, both reached through an SSH tunnel (architecture §7, production-debugging runbook).

## 6. fail2ban

```bash
sudo apt-get update && sudo apt-get install -y fail2ban
sudo tee /etc/fail2ban/jail.local >/dev/null <<'EOF'
[DEFAULT]
bantime = 1h
findtime = 10m
maxretry = 5

[sshd]
enabled = true
backend = systemd
EOF
sudo systemctl enable fail2ban && sudo systemctl restart fail2ban
sudo fail2ban-client status sshd
```

Five failed logins in 10 minutes ban an IP for an hour. Bots get banned within minutes of the server going online. If you ban yourself, wait an hour or use the provider's console: `sudo fail2ban-client set sshd unbanip <ip>`.

## 7. Automatic security updates

Ubuntu ships `unattended-upgrades`, enabled. Limit it to security sources and never reboot by itself, in a separate file so package upgrades don't overwrite it:

```bash
sudo tee /etc/apt/apt.conf.d/52quode-unattended-upgrades >/dev/null <<'EOF'
#clear "Unattended-Upgrade::Allowed-Origins";
Unattended-Upgrade::Allowed-Origins {
    "${distro_id}:${distro_codename}-security";
    "${distro_id}ESMApps:${distro_codename}-apps-security";
    "${distro_id}ESM:${distro_codename}-infra-security";
};
Unattended-Upgrade::Automatic-Reboot "false";
EOF
cat /etc/apt/apt.conf.d/20auto-upgrades                          # both lines "1"
sudo unattended-upgrade --dry-run --debug 2>&1 | grep -i "allowed origins"
```

When `/var/run/reboot-required` exists (kernel updates), reboot at a quiet moment: `sudo reboot`.

This covers Ubuntu's own packages only. Docker comes from Docker's repository and is **not** updated automatically: run `sudo apt-get update && sudo apt-get upgrade` monthly, and right away when Docker publishes a security advisory.

## 8. Docker Engine and Compose

From Docker's own repository, not Ubuntu's `docker.io` package:

```bash
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
gpg --show-keys /etc/apt/keyrings/docker.asc   # must show 9DC8 5822 9FC7 DD38 854A E2D8 8D81 803C 0EBF CD88
sudo tee /etc/apt/sources.list.d/docker.sources >/dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo usermod -aG docker deploy
```

The group change applies from the next login: log out, SSH in again, then:

```bash
docker run --rm hello-world
docker version && docker compose version
```

**The `docker` group is root-equivalent:** anyone who can run `docker` can control the host. That's the normal trade-off on a single server, and why `deploy` accepts key logins only.

## 9. Final check

```bash
sudo sshd -T | grep -Ei '^(permitrootlogin|passwordauthentication)'   # both "no"
sudo ufw status                                                    # active; 22, 80, 443
sudo fail2ban-client status sshd                                   # jail running
sudo ls /etc/sudoers.d/                                            # only README: no leftover temporary files
sudo -k; sudo -v                                                   # asks for the password
docker compose version
sudo ss -tlnp                                                      # only :22 on a public address until the stack runs; then also 80/443, plus 5432/8081 on 127.0.0.1
```

## Notes

- **Temporary password-free sudo:** if you add one to automate the setup (`/etc/sudoers.d/90-…` with `NOPASSWD`), delete it at the end and check with `sudo -k; sudo -v`.
- **Root:** the root password is for the provider's console only. SSH as root is off.
- **GitHub Actions has its own key** in `~/.ssh/authorized_keys`, limited to `deploy.sh` with `command=…,restrict` (ADR-0042, set up in `deploy/README.md`). Your own key's line has no such prefix; never add one to it.
- **Next:** the production stack runs from `deploy/` (M0-10) and deploys itself on every merge (M0-11). Backups come in M0-12.
